# DeviceArray benchmarks — Phase 3

Date: 2026-08-28  
Host: Apple M3, macOS 27.0, arm64  
Build: Release, Apple Clang 21, Metal runtime shader compilation, OpenCL 1.2

The benchmark target is the existing `benchmarks/src/bm_apple_backends.cpp`
source (the equivalent Phase 3 benchmark source). Build it with:

```text
cmake --build build-fixed --target highmap_benchmarks -j4
```

The registered resident chain sizes are 256², 512², 1024², 2048² and 4096².
The 8192² resident Chain A case is extended-only:

```text
HIGHMAP_PHASE3_EXTENDED=1 build-fixed/bin/highmap_benchmarks \
  --benchmark_filter='BM_Phase3_DeviceArrayShared_ChainA/8192'
```

Times below are representative single-run wall times in milliseconds from the
Release benchmark executable. GPU scheduling varies between runs, so the
tables are evidence of execution shape and direction, not a statistical claim.
OpenCL `device_or_finish_ms` is its blocking finish proxy, as in the Phase 2
benchmark document.

## Composed chains

Chain A is `Noise(42) → Gradient → SmoothMaximum`, with a second resident noise
field. It intentionally has no host input upload because both source fields are
generated by the resident noise operation. Chains B and C upload the required
terrain, field, dx, dy and talus maps once at the start.

Chain B is `Advection → Thermal(10)`. Chain C is
`Advection → Thermal(10) → HydraulicVPipes(10, maintain volume)`.

The main residency comparison is resident Shared versus synchronous Metal:

* Chain A improves by about 2.7× at 256², 3.9× at 512², 5.1× at 1024²,
  3.8× at 2048² and 3.9× at 4096² in these samples.
* Chain B is close at 1024² because five required inputs still cross the host
  boundary; its resident form removes intermediate transfers but cannot remove
  those required initial uploads.
* Chain C improves by about 1.6× at 256², 1.4× at 512² and 1.2× at 1024².
  The absolute benefit grows with hydraulic work even when the ratio narrows.

The resident tests assert one final readback and one synchronization for a
chain. Multi-input chains necessarily upload each distinct input once; the
assertion is about eliminating intermediate host-visible transfers, not about
pretending those inputs do not exist.

## Command-buffer experiment

At 1024² Chain A, three-repeat medians were approximately 3.52 ms for the
one-buffer path and 3.31 ms for the two-split-buffer path, both with one final
synchronization. The difference was within the observed driver variability,
so one command buffer remains the simpler default. The split path exists as a
real no-wait experiment and is covered by a correctness test.

## Buffer versus texture advection

The texture benchmark uses resident inputs and one final buffer output. It
creates six temporary `R32Float` textures and records six blit encoders (five
uploads and one output conversion). Representative wall times:

| Size | resident buffer advection | resident texture advection | texture / buffer |
|---|---:|---:|---:|
| 1024² | 8.181 ms | **5.877 ms** | 0.72× |
| 2048² | **28.262 ms** | 30.452 ms | 1.08× |
| 4096² | 249.976 ms | **185.016 ms** | 0.74× |

The result is mixed and includes conversion cost. The texture path is therefore
kept as an experiment; the buffer-backed API remains the default because it
has the smaller ownership surface and avoids mandatory conversions.
